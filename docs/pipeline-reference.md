# Flow file reference

A flow is one YAML file in the `.truss/flows/` folder of a [project](#project-layout). This
page lists every field of schema version `"1"`. Unknown fields are rejected everywhere, so a
typo never changes what runs.

Check a flow at any time without running it:

```console
$ truss validate nightly
.truss/flows/nightly.yaml is valid: flow nightly, 3 steps, concurrency 2
```

## Project layout

A project is a folder with a project file, `truss.yaml`, at its root. The project file names the
project and nothing else. Flows live beside it, one file each. See
[ADR 0015](decisions/0015-project-layout.md) for the reasons.

```text
my-project/
├── truss.yaml              # project file: name and description only
└── .truss/
    ├── .gitignore          # written by TRUSS: ignores state/
    ├── flows/              # pipelines, one file each: commit these
    │   ├── build.yaml
    │   └── nightly.yml
    └── state/              # generated by runs: not committed
        └── build/
            ├── run.log
            └── data/
                └── cache/
```

### Project file

```yaml
# truss.yaml
version: "1"

project:
  name: my-project                       # required
  description: Build and release tools   # optional

env:                                     # optional; for every flow of the project
  REGION: eu
```

| Field | Meaning |
|---|---|
| `version` | The string `"1"`. |
| `project.name` | Required. The same characters as a registry name: it starts with a letter or digit, then letters, digits, `.`, `_` or `-`. |
| `project.description` | Optional free text. |
| `env` | Optional. Variables every flow of the project gets, under the flow's own `env`. Same rules as a flow's [`env`](#env), `${NAME}` included. |

Any other field is an error. The error names the field and where it appears, never its value.
A `truss.yaml` in the project root with `steps` or `jobs` is rejected: those belong in a file in `.truss/flows/`.

### Flow files

- Flows are the files directly in `.truss/flows/`, named `<name>.yaml` or `<name>.yml`.
- The file name without its extension is the name you use on the command line: `truss run build`
  runs `.truss/flows/build.yaml`.
- Only regular files count. Folders, links, hidden files (names that start with `.`), cloud-sync
  placeholder files and other extensions are ignored, so a flow that disappears from the list is
  probably one of these. The extension is case-sensitive: `.YAML` is not accepted.
- Two files that differ only by letter case, or `build.yaml` next to `build.yml`, are an error.
  The error names both files.
- A name must start with a letter or digit, then use only letters, digits, `.`, `_` and `-`. It
  must not end in a dot or a space, and it must not be a Windows device name (`CON`, `PRN`, `AUX`,
  `NUL`, `COM1` to `COM9`, `LPT1` to `LPT9`).
- A flow file is at most 1 MiB. A larger file, or one that cannot be read or parsed, is an
  error. TRUSS never skips a broken flow.
- `.truss` and `.truss/flows` must be real folders, not links. A flows folder with more than 256
  entries is an error.

A flow given by path (`truss run ./other/build.yaml`) has the same 1 MiB size limit. TRUSS follows a link for an explicit path argument.
Its name is the file name without its extension.

### The project root

The project root is the working directory. TRUSS looks in that folder only and never in parent
folders. If a command needs a project and finds no `truss.yaml`, it names the folder it looked in.
Run commands from the project root.

### State folders

A run keeps its generated files in `.truss/state/<name>/`, where `<name>` is the flow's file
name without the extension:

| Path | Holds |
|---|---|
| `run.log` | The run log. The same text `truss run` prints. The last finished run is kept. |
| `data/` | The data folder: `TRUSS_DATA_DIR`. |
| `data/cache/` | The cache folder: `TRUSS_CACHE_DIR`. |

- These folders are private (mode `0700`) and TRUSS creates them with no links followed.
- The first time TRUSS creates `.truss/state`, it also writes `.truss/.gitignore` containing
  `state/`. TRUSS never changes an existing `.truss/.gitignore`. If it cannot write the file, it
  prints a `warning:` and the run goes on. Git then ignores the state folders and nothing else.
- Older builds wrote `.truss/run.log` and `.truss/data`. TRUSS ignores both. Delete them by hand
  when you like.

## At a glance

```yaml
# .truss/flows/nightly.yaml
version: "1"                  # required

flow:
  name: nightly               # optional; default: the file name
  concurrency: 2              # steps at once; default 1
  overlap: queue              # queue | skip | parallel; default queue
  workdir: app                # where steps start; default: the run's directory

on:                           # optional; needs the daemon
  schedule:
    - cron: "0 9 * * 1-5"     # weekdays at 09:00
      timezone: Europe/Berlin # default: the machine's local time
      missed: skip            # skip | run; default skip

env:                          # optional; for every step
  STAGE: nightly

jobs:                         # either jobs ...
  build:
    steps:
      - id: compile
        run: make build
        timeout: 10m
  test:
    needs: [build]
    env:
      GOFLAGS: -race
    steps:
      - id: unit
        run: make test
        dir: services/api

# steps:                      # ... or a flat list of steps
#   - id: hello
#     run: echo hello
```

## Top level

| Field | Required | Meaning |
|---|---|---|
| `version` | yes | The string `"1"`. A bare number `1` is rejected. |
| `flow` | yes | Name and run settings. Before v0.3.0 this block was called `pipeline`; that name is still accepted, but a file holds one or the other. |
| `on` | no | What starts the flow besides you. |
| `env` | no | Environment variables for every step. |
| `secrets` | no | Names of stored secrets for every step. |
| `steps` | one of the two | A list of steps that may depend on each other. |
| `jobs` | one of the two | Named groups of steps that depend on each other. |

A file has `steps` or `jobs`, never both.

## `flow`

The flow's name and how it runs. Files written before v0.3.0 call this block `pipeline:`; TRUSS
reads both, and `truss validate` rejects a file that has both.

| Field | Default | Meaning |
|---|---|---|
| `name` | the file name | Optional. Shown in logs and used as the name the daemon knows the flow by. Defaults to the file name without its extension. When it differs from the file name, `truss validate` prints a note. |
| `concurrency` | `1` | The most steps that run at the same time. A whole number of at least 1. |
| `workdir` | the run's directory | The directory steps start in: relative to where the run starts (the project root for `truss run` and for a flow in `.truss/flows/`; otherwise the file's directory), or absolute. A job's or step's `dir` replaces it. The directory must exist, or the step fails with a diagnostic and no exit code. |
| `overlap` | `queue` | What happens when a run is requested while another run of this flow is still active. Used by the daemon. |
| `kill_timeout` | `10s` | The default `kill_timeout` of every step. |

`overlap` values:

| Value | A second run request ... |
|---|---|
| `queue` | waits and starts when the first run ends. |
| `skip` | is dropped and recorded as skipped. Good for schedules that must not pile up. |
| `parallel` | starts next to the first run. |

## `on.schedule`

A list of cron triggers. They only fire while the [daemon](daemon.md) runs and the flow is
registered. `truss run` ignores them.

| Field | Default | Meaning |
|---|---|---|
| `cron` | required | Five fields: minute, hour, day of month, month, day of week. |
| `timezone` | local time | An IANA zone such as `Europe/Berlin` or `UTC`. |
| `missed` | `skip` | What to do with a time that passed while nothing watched the clock. |

Cron syntax:

| Form | Example | Meaning |
|---|---|---|
| value | `30 18 * * *` | every day at 18:30 |
| list | `0 8,17 * * *` | at 08:00 and 17:00 |
| range | `0 9 * * 1-5` | Monday to Friday at 09:00 |
| step | `*/15 * * * *` | every 15 minutes |
| names | `0 9 * * mon-fri`, `0 0 1 jan *` | three-letter weekdays and months |
| shortcut | `@hourly` `@daily` `@weekly` `@monthly` `@yearly` | the usual meanings |

Sunday is `0` or `7`. When both day fields are restricted, a day matches if either one does
(`0 0 13 * 5` is the 13th and every Friday), as in classic cron.

### Missed times

A laptop is not a server: it sleeps, and it is off at night. TRUSS never surprises you with a
late run by default.

| `missed` | The time passed while the machine was off, asleep, or the daemon was stopped |
|---|---|
| `skip` | Nothing runs. The history shows a skipped run with the time it was planned for. |
| `run` | One catch-up run starts as soon as the daemon is back, however many times were missed. |

A schedule counts as on time when it fires within two minutes of its planned time.

## `on.file`: start when files change

```yaml
on:
  file:
    paths: [inbox/, "src/**/*.go"]   # what to watch
    ignore: ["**/*.tmp"]              # optional: changes that do not count
    debounce: 5s                      # optional: wait until changes stop (default 2s)
```

The daemon starts the flow once files under `paths` were created, changed or removed, and no
further change came for `debounce`. A burst of changes is one run.

| Field | Meaning |
|---|---|
| `paths` | Required. Folders (everything under them), files, or patterns, relative to the project root or absolute. `*` and `?` match within a name, `**` across folders. Use `/` on every system. |
| `ignore` | Patterns of changes that do not count. |
| `debounce` | How long changes must stop, `1s` to `10m`. Default `2s`. |

- The run's trigger is `file`. `$TRUSS_CHANGED_FILES` names a file that lists the changed paths,
  one per line, relative to the project root (absolute for an absolute pattern).
- `paths` cannot go up with `..`: write a folder outside the project as an absolute path.
- An `ignore` pattern that matches a folder keeps the daemon out of it, which keeps scans fast
  (`ignore: [node_modules]`).
- Only while the daemon runs, and only for a registered flow that is not paused. Changes made while
  the daemon was stopped start nothing: the daemon looks at the files when it starts and counts
  changes from there.
- `.truss/state/` and `.git/` are never watched, so a flow that writes its own state does not
  start itself. A flow that writes into the folders it watches does: keep its output elsewhere, or
  `ignore` it.
- The daemon looks every second, at no more than 10,000 matching files and 50,000 files and
  folders per flow; narrow `paths` for big trees. It does not follow links: name the real folder.
- A flow has at most one run started by a hook at a time. Changes made while it runs start one
  more run when it ends.
- Patterns match names as written: `*.jpg` does not match `A.JPG`, even on Windows and macOS.
  A file is "changed" when its time or size changes; some disks keep times to the second, so write
  files in place with care, or write elsewhere and rename them in.
- A file whose name holds a line break or another control character is left out (the daemon log
  says so), because `$TRUSS_CHANGED_FILES` is one path per line.
- A whole disk (`/`, `C:/`) and `~` cannot be watched; at most three `**` per pattern.

## `on.run`: start when another flow ends

```yaml
on:
  run:
    flow: build
    status: succeeded          # succeeded (default), failed, any; or a list
```

`on.run` may be a list to follow several flows. The run's trigger is `run`. A run of `build` that
ran and ended as asked starts this flow, whatever started `build`; a run that never started (for
example cancelled while queued) starts nothing. While a run of this flow that a hook started is
queued or running, another one does not start. Flows that start each other in a loop stop after
10 runs in a row; the daemon log says so.

## `env`

A mapping of variable names to values, allowed at the top level, on a job, and on a step.
Later levels win: step over job over flow over the environment the run started from.
Values are taken as text, so `RETRIES: 3` sets the string `3`.

The project file `truss.yaml` may hold an `env` too: it is the lowest level, under the flow's own,
for every flow of the project ([Project file](#project-file)).

### Using one variable in another: `${NAME}`

A value of `env`, and a `dir` or `workdir`, may use other variables with `${NAME}`:

```yaml
# truss.yaml
env:
  DATA: ${HOME}/data            # from your environment

# .truss/flows/sync.yaml
env:
  INBOX: ${DATA}/inbox          # from the project
  PATH: ${TRUSS_PROJECT_DIR}/bin:${PATH}
steps:
  - id: sort
    dir: ${INBOX}
    run: ./sort-photos
```

- `${NAME}` takes the value from the same level, a lower level, the built-in variables or the
  environment TRUSS started in. A variable that is not set gives an empty text.
- `${NAME}` inside the value of `NAME` itself is the value from below, so
  `PATH: ${TRUSS_PROJECT_DIR}/bin:${PATH}` adds to your `PATH`.
- Order within a level does not matter. Two variables that use each other fail the step before it
  starts.
- `$$` is a literal `$`. A `$` before anything else stays as written, so `$HOME` is left for the
  shell of the step.
- Stored secrets are not expanded: `${TOKEN}` never copies a secret from the store into another
  variable. A variable of your own environment with that name is used like any other, and only
  stored secrets are hidden in output.
- A `dir` that uses a variable that is not set fails the step, rather than running somewhere else.
- `--env NAME=VALUE` on the command line is taken as written, and may set a built-in, to try a
  step as the daemon would run it.
- The value reaches the step as an environment variable. In `run`, quote it as your shell needs:
  `cd "$INBOX"`.

### Built-in variables

TRUSS sets these in every run, by hand, by the daemon or tracked. A file may not set them
(`truss validate` says so), and they win over a variable of the same name in your environment.

| Variable | Value |
|---|---|
| `TRUSS_FLOW` | The flow's name (the registered name for the daemon). |
| `TRUSS_PIPELINE` | The same, under its older name. |
| `TRUSS_STEP` | The step's id as written in the file. |
| `TRUSS_JOB` | The job's id; set only for a step of a job. |
| `TRUSS_ATTEMPT` | `1`, then `2` and up for each retry. |
| `TRUSS_RUN_ID` | The run's id; a local run that the daemon does not track gets `local-<time>-<random>`. |
| `TRUSS_TRIGGER` | `manual`, `schedule`, `catch-up`, `file`, `run`, or `local` for `truss run`. |
| `TRUSS_PROJECT_DIR` | The flow's project root, wherever you start the run, or the run's directory for a flow outside a project. |
| `TRUSS_TEMP_DIR` | A folder for this run only, removed when the run ends. |
| `TRUSS_CHANGED_FILES` | For a run that [`on.file`](#onfile-start-when-files-change) started: a file listing the changed paths. |
| `TRUSS_OS`, `TRUSS_ARCH` | `linux`, `darwin` or `windows`, and `amd64` or `arm64`. |
| `TRUSS_DATA_DIR`, `TRUSS_CACHE_DIR` | Folders that outlive runs ([below](#data-and-cache-folders)). A file may set these two. |

Other names starting with `TRUSS_` are yours to use, but later versions may add built-ins; pick
another prefix to be safe.

Do not put secrets in `env`: the file is plain text. Use [`secrets`](#secrets).

## `secrets`

A list of secret names, allowed at the top level, on a job, and on a step. Each name must be
stored first with `truss secret set <name>` (see [the CLI](cli.md#secrets)). A declared secret
becomes an environment variable of the same name in the steps that declare it, directly or
through their job or the flow, and in no other step. It overrides an `env` entry or an inherited variable of the same name.

```yaml
secrets: [GITHUB_TOKEN]          # every step
jobs:
  publish:
    steps:
      - id: npm
        run: npm publish
        secrets: [NPM_TOKEN]     # this step only
```

- A secret that is not stored fails the run **before any step starts**. The error lists the
  missing names and says `truss secret set <name>`. `truss run` exits 1; a daemon run is
  recorded as failed.
- Names follow the rule for `env` names. A repeated name, a non-list or a non-string is a
  validation error. `truss validate` lists the names a step uses and does not read the store.
- A flow that declares no secret never reads the store.

**Redaction.** In a run of a flow that declares secrets, every stored value (not only the
declared ones) that appears in step output is replaced by `***` in the run log,
`.truss/state/<name>/run.log`, the daemon's stored log, the API and Desktop. A value split over several
output chunks is still caught.

Redaction is exact text matching. It **cannot** catch a value that a step:

- encodes or transforms (base64, hex, URL encoding, upper case, reversed, characters inserted);
- splits across lines of its own;
- writes to a file, sends over the network or passes to another program's own log.

A very short secret is replaced wherever it appears, which can garble unrelated output. Do not
print secrets from a step, and do not run `set -x` or `env` in a step that has them.

## `steps`

Each step is one command for the host shell (`/bin/sh -c` on Linux and macOS, `cmd /c` on
Windows). Every step starts a new shell, so `cd` or `export` in one step does not carry over.

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Unique within the list. |
| `run` | yes | The command line, as you would type it. |
| `needs` | no | Ids of steps that must succeed first. Top-level steps only. |
| `env` | no | Variables for this step. |
| `secrets` | no | Stored secrets for this step. |
| `dir` | no | Working directory, relative to where the run starts: the project root for `truss run` and for a flow in `.truss/flows/`, otherwise the file's directory. |
| `timeout` | no | Ends the step when it runs longer: `90s`, `5m`, `1h30m`. |
| `kill_timeout` | no | How long the step has to end by itself once TRUSS stops it (timeout, cancel, a failure elsewhere, `daemon stop`), before it is killed. Default `10s`, or the flow's `kill_timeout`. See [How a step is stopped](#how-a-step-is-stopped). |
| `retries` | no | Extra attempts after a failure, 0 to 100. Default 0. See [Retries](#retries). |
| `retry_delay` | no | Wait before each retry, same format as `timeout`. Needs `retries`. |
| `continue-on-error` | no | `true` lets the run go on when this step fails. Default `false`. |
| `if` | no | A condition; the step runs only when it holds. See [Conditions](#conditions). |

A step's working directory is the first one set of: its own `dir`, its job's `dir`,
`flow.workdir`, the run's starting directory. They replace each other; they are not joined,
so a relative `dir` is always relative to the run's starting directory, not to `workdir`.
The run's starting directory is the project root for `truss run`. On
Windows a path with a drive letter must be absolute (`C:\work`, not `C:work`); `\work` means
that folder on the drive the run starts on.

Top-level steps form a graph through `needs`. A step starts when everything it needs has
succeeded and a concurrency slot is free. Without `needs` and with the default concurrency,
steps simply run top to bottom.

## `jobs`

A job is a named list of steps for one purpose: build, test, deploy.

| Field | Required | Meaning |
|---|---|---|
| `steps` | yes | Run in the order written, one after another. |
| `needs` | no | Ids of jobs that must succeed first. |
| `env` | no | Variables for every step of the job. |
| `secrets` | no | Stored secrets for every step of the job. |
| `dir` | no | Working directory for the job's steps; a step's own `dir` replaces it. |
| `if` | no | A condition for the whole job, checked once when its first step is ready. |

Job ids use letters, digits, `.`, `_` and `-`. In logs and in TRUSS Desktop a step of a job is
named `job/step`, for example `build/compile`.

Jobs that do not need each other run side by side when `flow.concurrency` allows it:

```yaml
# .truss/flows/ci.yaml
version: "1"

flow:
  name: ci
  concurrency: 3

jobs:
  lint:  { steps: [{ id: vet,  run: go vet ./... }] }
  test:  { steps: [{ id: unit, run: go test ./... }] }
  build:
    needs: [lint, test]
    steps:
      - { id: compile, run: go build ./... }
```

## Data and cache folders

Every run gets two folders that outlive the run. Steps find them in variables:

| Variable | `truss run` | Daemon run |
|---|---|---|
| `TRUSS_DATA_DIR` | `.truss/state/<name>/data` in the project | `~/.truss/pipelines/<name>/` |
| `TRUSS_CACHE_DIR` | `.truss/state/<name>/data/cache` | `~/.truss/pipelines/<name>/cache` |

TRUSS creates both before the first step and never empties them. What goes in is up to your
steps: a package cache, a downloaded toolchain. There are no cache keys, no saving or
restoring, and no clean workspace per run; the folders are plain directories. For `truss run`,
`<name>` is the flow's file name without its extension; for the daemon, it is the registered
name. `.truss/state/` is ignored by git, as described in [Project layout](#state-folders). Flow
`env` can override both variables like any other. To clear a cache see
[the daemon page](daemon.md#data-and-cache-folders).

## How a step is stopped

TRUSS stops a step when its `timeout` passes, when you cancel the run (`truss cancel`, Ctrl-C),
when another step fails and the run ends early, and when the daemon stops.

- **Linux and macOS:** every process the step started gets `SIGTERM`, so a script can clean up
  (`trap 'rm -f "$LOCK"' TERM`). Whatever still runs after `kill_timeout` (default `10s`, at most
  `1m`) gets `SIGKILL`. During `truss run`, a second Ctrl-C kills at once.
- **Windows:** the step and everything it started end at once; Windows has no request to stop
  that reaches every process, so `kill_timeout` has no effect there.
- A process that leaves the step's process group on Linux or macOS (`setsid`, a daemonizing
  tool) is neither asked nor killed.
- A stopped step fails, even if it handles the stop and exits `0`; `if: failure()` steps run.
- If the daemon process itself dies, on Windows its steps end with it. On Linux and macOS a step
  can outlive a crashed daemon; the run is marked failed when the daemon starts again.

## When something fails

The first failed step fails the run. Steps that are still running are stopped, and nothing new
starts, except the steps that ask for it with `if: always()` or `if: failure()`. A step fails
when its command exits with a non-zero code, cannot start, is ended by a signal, or runs past
its `timeout`. `truss run` then exits 1.

### Retries

```yaml
- id: fetch
  run: curl -fsS https://example.com/data.json -o data.json
  retries: 2          # at most 3 attempts
  retry_delay: 10s    # wait between attempts
```

Any failed attempt is run again, and `timeout` applies to each attempt. The step's result is its
last attempt. In the run log every attempt has its own lines:

```text
==== Step fetch ====
step fetch started
step fetch finished duration 0.210s exit 22
step fetch retry 2 of 3 in 10.000s
==== Step fetch ====
step fetch started
step fetch finished duration 0.180s exit 0
```

A step is not retried when the run is interrupted, or when TRUSS stopped it because another step
failed the run. A step that is waiting to retry at that moment is stopped. A step whose `if`
calls `always()` or `failure()` and that starts after the run failed is retried normally.

### continue-on-error

```yaml
- id: lint
  run: make lint
  continue-on-error: true
```

The failure is logged and shown, but the run does not fail, `truss run` can still exit 0, and
other steps keep going. A step that `needs` a failed `continue-on-error` step is skipped, unless
its `if` says otherwise (for example `if: failure()`).

### Conditions

`if` takes an expression. A step without `if` runs when every step it `needs` succeeded.

| Part | Meaning |
|---|---|
| `success()` | every step this step `needs` succeeded (always true without `needs`) |
| `failure()` | at least one step this step `needs` failed, was stopped, or timed out |
| `always()` | true |
| `env.NAME` | the value of NAME as the step would see it, or empty when unset |
| `'text'` or `"text"` | a literal, no escapes |
| `==` `!=` | compare two values |
| `!` `&&` `\|\|` `( )` | not, and, or, grouping |

An expression with no status function means `success() && (...)`. Quote the whole expression
when it starts with `!` or contains `: `.

```yaml
steps:
  - id: build
    run: make build
  - id: deploy
    needs: [build]
    if: env.STAGE == 'prod'
    run: make deploy
  - id: notify
    needs: [build, deploy]
    if: failure()
    run: ./tell-the-team.sh
  - id: cleanup
    needs: [build, deploy, notify]
    if: always()
    run: make clean
```

On a job, `if` is checked once, when the job's first step is ready. If it is false, every step
of the job is skipped; if it is true it replaces the default check for the first step (the jobs
it needs may have failed, for example a job with `if: always()`).

A skipped step is logged as `step deploy skipped because its if condition is false` (or `because
step build did not succeed`) and shown as skipped in TRUSS Desktop. The log never prints the
values an expression compared. A step with `always()` and no `needs` starts at once, so use
`needs` to run it last. After a failure only steps whose condition calls `always()` or
`failure()` start; `success()` and plain comparisons do not. The check is on the text of the expression: any
expression that calls `always()` or `failure()` counts, even inside `!`. A job's `if` with such a
call lets every step of that job start after a failure. A job whose first step is skipped
because of the jobs it needs (or an earlier failure) is skipped as a whole.

## Recipes

**A scheduled job that must never overlap itself**

```yaml
# .truss/flows/sync-photos.yaml
version: "1"
flow:
  name: sync-photos
  overlap: skip
on:
  schedule:
    - cron: "*/10 * * * *"
steps:
  - id: sync
    run: rsync -a ~/Pictures/ /Volumes/backup/Pictures/
    timeout: 9m
```

**A morning job that still runs when the laptop opens late**

Add this `on:` block to a flow file in `.truss/flows/`:

```yaml
on:
  schedule:
    - cron: "0 9 * * 1-5"
      missed: run
```

**Fan out, then fan in**

```yaml
# .truss/flows/release.yaml
version: "1"
flow:
  name: release
  concurrency: 4
steps:
  - { id: build,   run: make build }
  - { id: unit,    run: make test,  needs: [build] }
  - { id: lint,    run: make lint,  needs: [build] }
  - { id: package, run: make dist,  needs: [unit, lint] }
```
