# Git commit

Commit when the user asks, or when the pipeline in `CLAUDE.md` says to commit (spec artifacts, finished work). Follow the repository's git safety rules: do not skip hooks, push only to your own feature branch when the pipeline says so (never to `develop` or `main`), and do not amend a commit that has been pushed or that you did not just create.

## Inspect first

Run these in parallel before drafting the message:

- `git status`
- `git diff` and `git diff --cached`
- `git log -12 --oneline`

Leave secrets (`.env`, credentials, keys) unstaged and warn if the user asked to include them. Do not create an empty commit.

## Group by topic

Do not put every change from the working tree into one commit. Cluster the diff into several commits, one topic each. A feature session, a task list, or "commit the changes" is not one topic.

A topic is one reason the tree changed: a behavior, a fix, a test suite for that behavior, or the docs that belong with it. Files that serve that reason go in that commit. Files that serve another reason wait for the next commit.

Before staging:

- Name the topics in the diff. Order them so a later topic can build on an earlier one.
- For each topic, list the files that belong to it and stage only those paths.
- Leave every other path unstaged until its own commit.
- When one file mixes two topics, stage the hunks that belong to the current topic and leave the rest.

One topic, and only then, is one commit. Two topics are two commits, even when they landed in the same session.

## Message

Use a conventional commit. The subject line always starts with a type:

| Type | Use for |
|---|---|
| `feat` | User-facing behavior |
| `fix` | A defect |
| `docs` | Documentation only |
| `test` | Tests only |
| `refactor` | Structure change with the same behavior |
| `perf` | Performance |
| `build` | Build or dependencies |
| `ci` | CI or release automation |
| `chore` | Maintenance that fits none of the above |
| `style` | Formatting only |
| `revert` | Reverting a commit |

Add a scope when one area is obvious: `ci(release):`, `fix(executor):`.

Subject rules:

- Imperative mood: "add", "fix", "require". Not "added" or "adds".
- One line, about 50–72 characters. Long enough to name the change and where it lands. Short enough to read in `git log --oneline`.
- No trailing period.

Body rules:

- A blank line after the subject, then bullet points of what was done.
- At least two bullets. Usually no more than six.
- Each bullet is one concrete change: what changed and, when it matters, why.
- Do not restate the subject, list every file, or narrate the session.

```
ci: test every change and publish releases from version tags

- Run lint, race tests, and the built binary on Linux, macOS, and Windows.
- Publish a GitHub Release only when the tag, go.mod, and changelog agree.
```

```
fix(executor): keep the step exit code when the shell cannot start

- Return the start error without an exit code when exec fails before the process runs.
- Stop the pipeline on that step so later steps stay unrun.
```

## Author identity and trailers

Every commit is authored by `afri-bit`. Before the first commit of a session run `git config user.name` and `git config user.email`; if the name is not `afri-bit` or the email is a tool address, set them for this repository only:

```bash
git config user.name afri-bit
git config user.email afribit.tech@gmail.com
```

`guard-git.sh` refuses `git commit` under any other identity, and CI (`commit-identity-check.sh`) fails a pull request that contains one.

A `Co-authored-by: Name <email>` trailer is **allowed** when a person or a tool helped, and is never required. When Claude wrote the commit, end the message with `Co-authored-by: Claude <noreply@anthropic.com>` after a blank line. The author stays `afri-bit`. Do not add `Signed-off-by`, session links or "generated by" lines.

Pass the message only through a HEREDOC:

```bash
git commit -m "$(cat <<'EOF'
type: subject of about fifty to seventy two characters

- First concrete change.
- Second concrete change.

EOF
)"
```

After the commit, read `git log -1 --format='%an <%ae>%n%B'`. If the author is not `afri-bit`, or a `Signed-off-by`, session link or "generated by" line was injected, and this commit is still unpushed, fix it with `git commit --amend --reset-author` and the same HEREDOC. Do not use `--no-verify`. Then run `git status` to confirm the tree is clean or that only intentional leftovers remain.
